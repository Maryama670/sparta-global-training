Database Schema vs API Schema — AML/Fraud Notes
**Database schema** - class is blue print and becomes an entity when it gets inside a database
The database schema is the blueprint for how operational AML data is stored.
It defines:
- Entities/tables: Alert, Account, Transaction, Rule, Analyst, Case
- Fields: alert_id, amount, status, rule_id
- Data types: str, int, float, datetime
- Primary keys: uniquely identify records, e.g. alert_id
- Foreign keys: connect tables, e.g. rule_id, account_id, analyst_id
- Relationships: one account can have many alerts; one analyst can handle many alerts
- Constraints: uniqueness, required fields, valid database values
Example:
Alert
├── alert_id      PRIMARY KEY
├── account_id    FOREIGN KEY
├── rule_id       FOREIGN KEY
├── analyst_id    FOREIGN KEY
├── amount
├── corridor
└── status

**API schema**
The API schema defines what data FastAPI is allowed to receive, validate and return.
Usually built with Pydantic.
The same Alert entity can have several API schemas:
CreateAlert
UpdateAlert
AlertResponse

These are not three separate database objects. They are different representations of the same Alert.
For example:
class CreateAlert(BaseModel):    account_id: str    amount: float    rule_id: str
class UpdateAlert(BaseModel):    status: str    analyst_id: str | None = None
class AlertResponse(BaseModel):    alert_id: str    account_id: str    amount: float    status: str

Validation
Type validation:
amount: float

means amount must be numeric.
Format validation:
alert_id: str = Field(pattern=r"^ALT-\d{3}$")

means:
ALT-001 ✅
donuts ❌
ALT-ABC ❌

Database primary keys then add another protection:
Pydantic → correct format
Database → unique ID
Lookup → ID actually exists

Simple distinction: database schema = how data lives; API schema = how data enters and leaves the system.
